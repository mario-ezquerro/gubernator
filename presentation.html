[PARADIGM // WHY GUBERNATOR?] 02 / 08

El Dilema de la Orquestación Modern

¿Por qué crear un nuevo orquestador de contenedores?

❌ Kubernetes (k8s)
• Excesiva complejidad cognitiva y de mantenimiento.
• Consumo masivo de RAM en idle (>1.5 GB por nodo).
• Requiere equipos dedicados de DevOps/SRE.
⚠️ Docker Swarm
• Sencillo pero limitado en targeting hardware avanzado.
• Falta de abstracciones finas para cargas mixtas/AI.
• Proyectos de comunidad estancados.
✅ Gubernator (The Goldilocks Solution)
• Sencillez de Swarm: `docker-compose.yml` nativo.
• Flexibilidad de Nomad: Target por hardware (`gpu=nvidia`, `arch=arm64`).
• Ligero: Consumo < 20 MB RAM en Go.
[ROMAN_LEGION // ARCHITECTURE] 03 / 08

Arquitectura: Manager & Centurions

  • Single Binary Architecture: El mismo binario gbnt actúa como Central Manager o Worker Agent.
  • Manager Node (Imperium):
    • REST API (:4000) protegida por Bearer Tokens (`GBNT_API_TOKEN`).
    • Dashboard Web (:4001) en Flutter con Material 3 y autenticación SSO.
    • Telemetría y Swagger (:4002) aislado para observabilidad.
  • Worker Nodes (Centurions):
    • Registro mediante Handshake JWT / Secret Token.
    • Heartbeats periódicos con estado de salud (Active / Pause / Drain).
    • Caché SQLite local en modo "Draft" para seguir operando si se pierde el enlace con el Manager.

[SCHEDULER // HARDWARE_TARGETING] 04 / 08

Deployment Engine & Label Matching

Despliegue de pilas de servicios con selección inteligente de hardware.

docker-compose.yml

version: '3.8'
services:
  ai-inference-service:
    image: ollama/ollama:latest
    ports:
      - "11434:11434"
    deploy:
      replicas: 2
      placement:
        constraints:
          - node.labels.gpu == nvidia
          - node.labels.zone == europe-1
          - stack.name == ai-cluster

Motor de Coincidencia de Etiquetas

  • Convención de etiquetas con prefijo temático romano / gubernator:
    gbnt.node.role=worker
    gbnt.node.gpu=nvidia
    gbnt.node.zone=europe-1
  • El Scheduler evalúa las restricciones de ubicación (`deploy.placement.constraints`) y distribuye las tareas únicamente en los nodos calificados.
  • Algoritmo de balanceo Least Loaded / Spread integrado.
[AQUEDUCTS // SERVICE_DISCOVERY] 05 / 08

Los Acueductos: CoreDNS + Caddy Ingress

🌐 CoreDNS Centralizado (*.gbnt)
• Instancia centralizada gbnt-coredns ejecutándose en el nodo Manager.
• Gubernator actualiza de forma dinámica las entradas de resolución interna DNS conforme los contenedores se despliegan o se reinician.
• Todos los nodos y contenedores resuelven nombres internos como web.my-stack.gbnt.
⚡ Ingress con Caddy Proxy
• Detección automática de etiquetas de enrutamiento exterior.
• Generación y recarga en caliente del Caddyfile.
• Certificados TLS automáticos y proxy inverso a los contenedores desplegados en el cluster. 
[Container Request] ---> [CoreDNS :53 (Manager)] ---> Resolve internal IP (192.168.252.12)
[External Web Client] -> [Caddy Ingress :80/:443] --> Reverse Proxy to container port

Consola Shell Integrada y Resiliencia HTTP

[FUTURE_HORIZONS // ROADMAP] 08 / 08

La Expansión del Senado (Roadmap Futuro)

🏛️ High Availability (rqlite / dqlite)
Evolución hacia SQLite distribuido sobre el protocolo Raft. Permite clusters de 3 a 5 Managers sin punto único de fallo (SPOF).
🛡️ Vault de Secretos Integrado
Inyección segura de contraseñas y certificados cifrados dentro de los contenedores sin revelar contraseñas en texto plano.
🔄 Rolling Updates Zero-Downtime
Despliegue secuencial de contenedores verificando healthchecks antes de dar de baja versiones anteriores.
💾 Storage & Volume Affinity
El Scheduler conoce la ubicación física de los volúmenes de datos y reprograma contenedores en el mismo nodo físico.
